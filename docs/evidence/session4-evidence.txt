=== Exercise 8: Polly v8 Resilience with Realistic Failure Simulation ===

503 retry path confirmed:
  Retry #1 after 865ms (HttpRequestException)
  -> succeeded on second attempt, 200 OK with issued certificate

Hang path confirmed (every 7th internal attempt):
  20s simulated hang cut to ~5009ms by the outer AddTimeout(5s)
  -> Polly.Timeout.TimeoutRejectedException thrown, OnTimeout event fired
  -> surfaces as 500 (unhandled by controller's InvalidOperationException-only
     catch; a real production controller would map TimeoutRejectedException
     to a friendlier response)

400 path confirmed (every 11th internal attempt):
  No Retry #n log lines at all - CertificateService maps non-5xx failures to
  InvalidOperationException, which sits outside ShouldHandle's transient-only
  list (HttpRequestException, TimeoutRejectedException), so Polly correctly
  never retries a non-transient client error.

Circuit breaker: attempted to trip via burst testing (15-30 calls at various
MinimumThroughput/FailureRatio settings) but could not reliably trip it under
lab conditions. Root cause understood: pipeline order is Timeout ->
CircuitBreaker -> Retry, so the breaker only observes ONE outcome per
top-level call, after retries have already resolved most transient 503s
internally. Only fully-exhausted-retry or timed-out calls count as
breaker-visible failures, which the fake's realistic failure distribution
(n%3!=0 for 503, n%7==0 for hang) produces too rarely to cross even a
lowered threshold within a reasonable burst size. This matches the
handout's own troubleshooting guidance ("MinimumThroughput too high for
test volume... production value depends on real traffic"). The retry,
timeout, and non-retry-on-400 behaviors are all proven; circuit breaker
open/close transitions were not directly observed in this lab session,
though the breaker registration and configuration are in place and correct.

Step 4/5 (no code, concept only):
- AddStandardResilienceHandler() is the one-liner default (retry + breaker +
  per-attempt timeout + total timeout) for HTTP clients that don't need
  bespoke tuning.
- AddRateLimiter inside a Polly pipeline is a bulkhead (caps concurrent
  in-flight requests to a downstream); AddHedging issues a second request to
  a slow upstream for idempotent reads only, never for state-changing POSTs.
